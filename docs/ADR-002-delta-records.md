# ADR-002:Delta 历史存储(Work Log 的增量编码)

- **状态**:已采纳(Accepted)。
- **日期 / 基线**:2026-09-27,基于 v3.18.0(`ac164a6`),前置 ADR-001(分键布局,`bgtRecords` 独立键)。
- **关联**:手册 WP-5.1(总闸,阻塞 5.3/5.4;5.2 另被 4.1 阻塞)、§3"记录上限"。

---

## 1. 问题

`RECORDS_MAX = 300` 全量快照 ≈ 每天 2 次收工 **5 个月**就触顶滚动 —— 而知识库/花园的
价值恰恰在**长青**。这是手册认定的硬冲突:Delta 存储在 v4.0 路线上不是优化,是前置。

## 2. 决策

**内存全量、磁盘增量。**

- **写入**(`encodeRecords`):窗口(首条留存)存全量,后续每条存与上一条的差分 ——
  `added`(标签对象)/ `removed`(身份键)/ `order`(身份键序列,**仅当实际顺序
  与默认重建序不一致时才存**)。窗口 `RECORDS_MAX` 300 → **1000**(增量单条 ~0.1–1KB,
  1000 条 ≈ 16 个月@2 次/天)。
- **读取**(`expandRecords`,在 `load()` 内):按 `baseId` 链重建全量;**所有消费方
  (时间轴/身份索引/周报/统一搜索/证据段/备份)拿到的永远是全量记录,零改动**。
- **自描述**:有 `tabs` = 全量,有 `delta` = 增量。**旧数据零迁移** —— 升级当次
  首次落盘即自然转入增量形态。
- **断链不可能**:编码时的窗口截断自动把留存首条物化为全量;`expandRecords` 对
  异常断链(基缺失/损坏)采取"跳过该条、不产出错误数据"的宁缺毋错语义。

## 3. 顺序保真(刻意付出的代价)

标签顺序是"现场"的一部分 —— 还原现场不得重排。重建的默认序 = 基序(去掉 removed)
+ added 依 next 序追加;实际顺序与此一致时**省略 order**(追加型收工的常见形态,
增量 < 全量的 15%),不一致时显式存 order(实测换位型 ≈ 38%)。保真优先于压缩率。

## 4. 被否决的方案

- **维持 300 全量**:5 个月硬墙仍在,与花园目标直接冲突。
- **全量落盘 + 旁路 delta 索引**:两份真相,违背"派生视图不落盘"的架构原则。
- **整包压缩**:不解决"窗口按条数滚动"的语义,只改体积;且与分键写入模型不匹配。

## 5. 后果

- 备份(`makeFullBackup`)消费内存全量 ⇒ **备份格式不变、始终可移植**;恢复后再次
  落盘自然重新编码。
- 读取成本增加一次链展开 O(窗口总标签数),与旧"读全量"同数量级;`recordEqualsLast`
  去重基于全量 `hash`,语义不变。
- 验收断言(均在本 commit 落地):往返保真(含顺序)/ 窗口自动再基 / 体积收益
  (换位型 < 45%、追加型 < 15% 且 order 省略)/ 混合旧数据 / persist→load 端到端;
  变异验证:落盘退回全量 → 磁盘形态断言红。
